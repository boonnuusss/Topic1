# Project Review: Topic1 Ray-wise STEC-to-VTEC Pipeline

**Date:** 2026-06-25  
**Scope:** Full codebase, documentation, experimental history, and architecture  
**Reviewer:** Claude (Cowork agent)

---

## Overall Assessment

Topic1 is a well-organized, scientifically honest research codebase. The project has a clear scientific question (can ray-wise ML improve STEC-to-VTEC conversion over the traditional single-layer mapping model?), rigorous documentation, and a commendable culture of logging negative results. The code is clean and modular. The main areas needing attention are testing, a few code robustness issues, and the unsolved scientific challenge exposed by the most recent experiments.

Nine project-brain files in Markdown provide comprehensive onboarding: `README.md`, `RESEARCH_PLAN.md`, `DATA_DICTIONARY.md`, `TODO.md`, `FAILED_ATTEMPTS.md`, `EXPERIMENT_LOG.md`, `AGENT.md`, `IRI_SIMULATION_SCHEMA.md`, and `scripts/README.md`. ## Issues and Recommendations

### Critical: No Tests

**Problem:** There are no unit tests, integration tests, or test framework anywhere in the project. Core functions like `compute_slant_factor`, `map_sp3_prn`, `geodetic_to_ecef`, `regression_metrics`, and `config_from_mapping` have no automated verification.

**Recommendation:** Add a `tests/` directory with pytest-based tests for:

- `compute_slant_factor`: verify at 90 deg elevation returns ~1.0; verify at low elevation returns > 1.0
- `map_sp3_prn` / `constellation_from_prn`: round-trip for each constellation
- `geodetic_to_ecef` / `_ecef_to_geodetic`: round-trip to known reference points (e.g., (0,0,0) -> (6371,0,0) km approximately)
- `config_from_mapping`: verify defaults and overrides
- `regression_metrics` / `vtec_error_metrics`: known-error cases (perfect prediction, constant offset, NaN handling)
- `random_split` / `time_split` / `station_holdout_split`: verify sizes, no overlap, group integrity for holdout splits
- `add_time_features`: verify cyclical values are in [-1, 1], DOY 1 and DOY 365 encode similarly
- `read_sp3_to_xarray`: smoke test on a small known SP3 file

### Moderate: Code Robustness

**1. Per-call Transformer instantiation in `geometry.py`** (line 19)

```python
def geodetic_to_ecef(lon_deg, lat_deg, height_m=0.0):
    transformer = Transformer.from_crs("EPSG:4326", "EPSG:4978", always_xy=True)
```

`pyproj.Transformer` instantiation has non-trivial overhead (~tens of ms) from reading PROJ data files. When called in a loop over 200k rows, this adds up. Cache the transformer at module level:

```python
_transformer_to_ecef = None
def geodetic_to_ecef(lon_deg, lat_deg, height_m=0.0):
    global _transformer_to_ecef
    if _transformer_to_ecef is None:
        _transformer_to_ecef = Transformer.from_crs("EPSG:4326", "EPSG:4978", always_xy=True)
    return _transformer_to_ecef.transform(lon_deg, lat_deg, height_m)
```

Same issue applies to `_ecef_to_geodetic` in `io_sp3.py` (line 49).

**2. Fragile import style in `baselines.py`** (lines 7-10)

```python
try:
    from .geometry import compute_slant_factor
except ImportError:
    from geometry import compute_slant_factor
```

This silently falls back to an absolute import, which may import a different `geometry` module from `sys.path`. Prefer consistent relative imports and run entry points as `python -m src.<module>`.

**3. Hard-coded absolute path in `configs/quick_test.yaml`** (line 3)

```yaml
tec_data_dir: E:/Scientific_Research/data/gnssTECmatFiles
```

This path is specific to one machine. Consider using environment variables or a `.env` file with a placeholder in the committed config:

```yaml
tec_data_dir: ${TEC_DATA_DIR}
```

**4. `io_mat.py` station position extraction** (lines 78-81)

```python
station_lon = _field(mat, "StationLON").astype(float)
station_lat = _field(mat, "StationLAT").astype(float)
rec_lon = float(station_lon[0]) if len(station_lon) else np.nan
rec_lat = float(station_lat[0]) if len(station_lat) else np.nan
```

If station coordinates vary within a file (e.g., a mobile receiver), only the first value is used silently. Either assert uniqueness or compute statistics and warn.

**5. `metrics.py` elevation bin edge case** (lines 101-102)

```python
bins = [10, 20, 40, 60, 90]
labels = ["10-20", "20-40", "40-60", "60-90"]
```

`pd.cut` with `right=True` includes the right edge in the bin. Elevation = 20.0 goes to "10-20" (not "20-40"), and elevation = 10.0 goes to NaN because it's not > 10. This is a QC ambiguity — elevations are filtered at >= 10, so elevation = 10.0 exactly would be excluded from binning. Use `include_lowest=True` or set bins starting below 10.

### Minor: Architecture and Maintainability

**6. No logging framework.** The codebase uses `print()` statements. For a pipeline with multi-epoch processing that can take hours, structured logging (Python's `logging` module) would allow configurable verbosity, timestamps, and log-file output. This is especially useful for the IRI simulation builder, where per-epoch progress and PyIRI errors matter.

**7. Empty placeholder modules.** `src/models/temporal.py` defines `LAG_FEATURES = ["stec_lag_1", "stec_lag_3", "stec_lag_12"]` but the file is not imported or used anywhere. If this is future work, add a docstring saying so. If it's dead code, remove it.

**8. `requirements.txt` is minimally versioned.** Only `numpy` and `numexpr` have version constraints. For reproducibility, pin all direct dependencies with `>=` lower bounds (at minimum) and consider a lockfile (`pip freeze > requirements-lock.txt`). PyTorch especially needs a versioned constraint since the model architecture uses `BatchNorm1d` and `Dropout`.

**9. No type annotations on many functions.** Functions in `split.py` and `evaluate.py` lack return type hints. Annotating `-> pd.DataFrame` or `-> dict[str, float]` aids code review and IDE support.

**10. `scripts/` PowerShell files are missing from the repository.** The `scripts/README.md` documents wrappers like `build_quick_dataset.ps1` and `build_slm_vtec.ps1`, but `Glob("scripts/**/*")` returned no matching files. Either the scripts were not committed, or they live outside the glob path. This breaks the reproducibility goal — the Python commands are documented, but the wrappers are referenced as the primary interface.

### Minor: Scientific / Methodology

**11. Single train/test split for each experiment.** All experiments use one random/time/station/PRN split with a single seed (42 or 52). For robust conclusions, consider k-fold cross-validation (by station or time), or at minimum run multiple random seeds and report mean and std of metrics.

**12. Shell height sensitivity.** The 450 km shell height is used throughout without a sensitivity analysis. The project already records `shell_height_km` in every output — adding a sweep over [350, 400, 450, 500] for the SLM baseline would strengthen the physical baseline claim.

**13. VTEC evaluation at single epoch.** The main comparison is on UT05:00 only (Experiment 018/019/020). For a publishable result, the comparison must span multiple epochs and be aggregated properly across time.

**14. The core scientific challenge remains unsolved.** Experiments 019-022 demonstrate that training only on slant-ray STEC labels (without vertical-ray supervision or physical constraints) fails to generalize to vertical-ray queries for STEC-to-VTEC conversion. The current models — RayMLP and FNN — fit slant STEC well but produce VTEC estimates much worse than the classical SLM baseline. The experiment log identifies this clearly, but the `TODO.md` task "Compare SLM conversion and RayMLP-assisted conversion under random, time, station, and PRN splits" is not yet marked complete. The next steps should focus on architectural changes: physics-informed constraints (e.g., enforcing that the model output approaches the SLM mapping factor for high elevations), non-identity ray-supervision (training with varied target geometries), or hybrid approaches that blend ML with the SLM analytically.

## Summary

This is a mature, well-documented research codebase with strong scientific hygiene. The main vulnerability is the lack of automated testing. The architecture is clean and the separation of legacy vs. mainline code is handled well. The honest documentation of negative results in the experiment log is noteworthy and builds credibility. The core scientific challenge — training a model that can generalize from slant-ray STEC to vertical-ray VTEC queries better than the classical single-layer model — remains open, but the project has built an excellent experimental infrastructure for exploring it systematically.
